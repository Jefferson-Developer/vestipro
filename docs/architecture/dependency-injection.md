# Dependency Injection

VestiPro uses `get_it` with `injectable` as the single dependency injection mechanism.

## Bootstrap

- `lib/app/injection.dart` owns the global `getIt` instance and `configureDependencies`.
- App entrypoints call `bootstrap`, and `bootstrap` calls `configureDependencies` before `runApp`.
- Feature code must not call `GetIt.instance` directly. Dependency resolution belongs at the app
  composition boundary, usually through `BlocProvider`.

## Lifetimes

- Datasources are `@lazySingleton` because they represent reusable infrastructure adapters.
- Repository implementations are `@lazySingleton` and are bound to domain contracts with `as:`.
- Use cases are `@injectable`; they are stateless and can be rebuilt for each resolution.
- BLoCs/Cubits are `@injectable` factories so each screen flow receives a fresh instance.
- Constructors stay explicit. Classes receive dependencies through parameters instead of reading the
  container internally.

## Environments

`configureDependencies` passes the current flavor to `injectable` (`dev`, `staging`, or `prod`).
Environment-specific implementations should use `env:` or `@Environment` annotations instead of
branching inside widgets or domain services.

## Generated Code

`lib/app/injection.config.dart` is generated by:

```bash
flutter pub run build_runner build --delete-conflicting-outputs
```

The generated file is versioned with the source annotations so CI and local builds use the same
registration graph.
